# Storage benchmark baseline

The measured baseline for the phase-1 store. Generated by
[`graph-lite/bench/store_bench.cpp`](../../graph-lite/bench/store_bench.cpp) — a
deterministic, fixed-seed (12345) benchmark of the public C API with fixed
iteration counts and no timing assertions. Wall-clock numbers only.

- Build type: RelWithDebInfo (the `release` preset)
- Date: 2026-11-10 (UTC)
- Box: 4 cores, 15.6 GiB RAM, GCC 13.3.0 (Ubuntu 24.04), CMake 3.28.3, Ninja 1.11.1

## Reproduce

```
cmake --preset release
cmake --build --preset release --target graph_lite_bench
./build/release/graph-lite/graph_lite_bench
```

## Recorded run (2026-11-10)

```
graph-lite store benchmark (seed 12345, 3 walk repeats)
scenario               ops         ms        ns/op   bytes/node   bytes/edge
bulk_insert         600000      980.8         1635        658.5        131.7
forward_walk        300000      195.0          650           --           --
reverse_walk        300000      198.9          663           --           --
churn               350000     1809.3         5169           --           --
footprint                0         --           --        623.4        166.4
checksum 149974858045 (guard against dead-code elimination)
```

What each row measures:

- `bulk_insert` — cold start: 100k nodes then 500k random edges (self-loops and
  parallel edges included, as the API permits); footprint sampled right after.
- `forward_walk` / `reverse_walk` — degree query + full neighbor copy for every
  node, repeated 3 times (300k node visits total per row), forward and reverse.
- `churn` — remove every second node (each removal cascades its incident edges,
  which also exercises pool compaction), then re-add 50k nodes and 250k edges.
- `footprint` — `graph_lite_graph_memory_usage` after the churn: total bytes per
  live node and per live edge, fragmentation included.

## How to read this

These numbers are machine-relative: they mean something only on the box listed
above. When this file is regenerated after a storage change, compare TRENDS
against the previous table — a regression is a row getting consistently slower
or a footprint row growing at equal workload — and never quote these absolutes
in issue text, reviews, or other docs. Expect roughly ±20% run-to-run variance
on the wall-clock rows (an earlier run the same day measured `bulk_insert` at
800.5 ms); the `footprint` row is exact for a given seed and workload.

One measured observation worth keeping: forward and reverse walks land within
~2% of each other (650 vs 663 ns/op), as they should — the reverse direction is
materialized with the same structure as the forward one, and that symmetry is
the property this table should keep showing after future storage changes.
